# Enterprise Deployment Guide

## Overview

This guide covers deploying `linux-entra-bridge` in managed Linux desktop environments where IT admins need to pre-configure browsers for Microsoft Entra ID SSO.

## Prerequisites

- Microsoft Identity Broker enrolled (device registered in Intune)
- `microsoft-identity-broker.service` running (`systemctl --user status microsoft-identity-broker.service`)
- Edge SSO already working (verifies broker enrollment)
- Python 3.9+ with `dbus-python`

## Installation

### Option A: Pre-built package from OBS (recommended)

Packages are built for many distributions on the [openSUSE Build Service](https://build.opensuse.org/project/show/home:Pihaar:linux-entra-bridge). Add the repository for your distribution, then install. Examples:

**Fedora 43**
```bash
sudo dnf config-manager --add-repo https://download.opensuse.org/repositories/home:Pihaar:linux-entra-bridge/Fedora_43/home:Pihaar:linux-entra-bridge.repo
sudo dnf install linux-entra-bridge
```
**openSUSE Tumbleweed**
```bash
sudo zypper addrepo https://download.opensuse.org/repositories/home:Pihaar:linux-entra-bridge/openSUSE_Tumbleweed/home:Pihaar:linux-entra-bridge.repo
sudo zypper refresh && sudo zypper install linux-entra-bridge
```

For Debian, Rocky/RHEL, Leap, and other distributions see the [main README](../README.md#pre-built-packages-opensuse-build-service).

This installs:
- Native messaging host at `/usr/libexec/linux-entra-bridge/linux_entra_bridge.py`
- Native messaging manifests for Firefox, LibreWolf, Chromium, Chrome, Brave, Vivaldi
- Chromium unpacked extension at `/usr/share/linux-entra-bridge/extension/`

### Option B: Manual Install

```bash
git clone https://github.com/Pihaar/linux-entra-bridge.git
cd linux-entra-bridge && bash native-host/install.sh
```

## Browser Configuration

### Firefox / LibreWolf

Install the signed `.xpi` from the [Releases page](https://github.com/Pihaar/linux-entra-bridge/releases). Firefox does not support policy-based extension installation on Linux without an update server.

Users can install manually: `about:addons` → gear icon → "Install Add-on From File" → select `.xpi`.

### Chromium / Chrome / Brave / Vivaldi

#### 1. Allow the Extension

Deploy `contrib/chromium-policy.json` to the managed policy directory:

```bash
# Chromium
sudo cp contrib/chromium-policy.json /etc/chromium/policies/managed/linux-entra-bridge.json

# Google Chrome
sudo cp contrib/chromium-policy.json /etc/opt/chrome/policies/managed/linux-entra-bridge.json

# Brave
sudo mkdir -p /etc/brave/policies/managed
sudo cp contrib/chromium-policy.json /etc/brave/policies/managed/linux-entra-bridge.json
```

This adds the extension ID (`dffhogipdmkddjnppibgmgpcobdnaffk`) to the allowlist and pins it to the toolbar.

#### 2. Load the Extension

Users load the extension from the RPM-installed path:
1. Open `chrome://extensions` (or `brave://extensions`)
2. Enable **Developer mode**
3. Click **Load unpacked** → select `/usr/share/linux-entra-bridge/extension/`

> **Note:** Chromium's `force_installed` mode requires a Chrome Web Store update URL, which is not available for self-hosted extensions. The `allowed` + `ExtensionInstallAllowlist` approach is the practical path for RPM-distributed extensions.

## Stable Extension ID & Key Management

The Chromium extension ID is deterministically derived from the public key in the manifest:

```
dffhogipdmkddjnppibgmgpcobdnaffk
```

**Key details:**
- The `key` field in `manifests/chromium.json` is the **public key only** (RSA, base64-encoded)
- The corresponding private key is **not stored in the repository** — it was generated by Chrome on first "Load unpacked" and resides in the developer's browser profile
- The public key pins the extension ID: any installation with this manifest gets the same deterministic ID
- **Key rotation** would change the extension ID, breaking all native messaging host manifests (`allowed_origins`) and enterprise policy files (`ExtensionInstallAllowlist`)
- The public key is safe to commit — it cannot be used to forge extensions (Chrome verifies the manifest hash, not a signature, for unpacked extensions)

This ID is stable across all installations and is used in:
- Native messaging host manifests (`allowed_origins`)
- Enterprise policy files (`ExtensionInstallAllowlist`)

## Verification

After installation, verify SSO works:

1. Open the extension popup → should show "Connected to Identity Broker"
2. Navigate to an Entra ID protected service → SSO should succeed without Edge
3. Check `about:addons` (Firefox) or `chrome://extensions` (Chromium) for error messages

## Troubleshooting

- **"Native host not installed"**: Run `bash native-host/install.sh` or install the RPM
- **"Broker unhealthy"**: Check `systemctl --user status microsoft-identity-broker.service`
- **No accounts shown**: Ensure device is enrolled in Intune (Edge SSO must work first)
- **Cookie not set**: Open popup → check recent warnings in the log viewer

## SPA Background SSO (Enterprise Policy)

Admins can pre-configure which Microsoft SPA domains get Background SSO via managed storage. This auto-grants permissions without requiring the user to click the toggle per-domain.

**Chromium (via policy JSON):**

Deploy the `3rdparty.extensions.dffhogipdmkddjnppibgmgpcobdnaffk` section in your managed policy:

```json
{
  "3rdparty": {
    "extensions": {
      "dffhogipdmkddjnppibgmgpcobdnaffk": {
        "spaAllowedDomains": [
          "teams.microsoft.com",
          "outlook.office.com",
          "portal.azure.com"
        ]
      }
    }
  }
}
```

**Firefox (via policies.json at /etc/firefox/policies/):**

```json
{
  "policies": {
    "3rdparty": {
      "Extensions": {
        "entra-bridge@linux-entra-bridge": {
          "spaAllowedDomains": ["teams.microsoft.com", "outlook.office.com"]
        }
      }
    }
  }
}
```

**Domain validation rules:** Domains must be valid hostnames (e.g., `teams.microsoft.com`). Wildcards with leading `*.` are allowed (e.g., `*.sharepoint.com`). Invalid entries (containing `://`, `/`, or control characters) are silently ignored.

## Endpoint Security Prerequisites

### Full-Disk Encryption (FDE)

Endpoints running this extension handle Entra ID SSO tokens (in-memory only, never persisted to disk). However, the browser profile directory (`~/.mozilla/`, `~/.config/chromium/`) contains session data including the extension's `storage.local` (account selection preference). Full-disk encryption (LUKS/dm-crypt) is strongly recommended on endpoints handling Entra ID credentials.

Verify FDE status:
```bash
lsblk -o NAME,FSTYPE,MOUNTPOINT | grep crypt
```

### TPM 2.0

The `microsoft-identity-broker` D-Bus service uses TPM-bound device keys for PRT issuance. A TPM 2.0 module is required (implied by Intune enrollment).

Verify TPM:
```bash
tpm2_getcap properties-fixed 2>/dev/null | head -5 || cat /sys/class/tpm/tpm0/device/description
```

### EPP/EDR Coverage

Endpoints should have active Endpoint Protection Platform (EPP) and/or Endpoint Detection and Response (EDR) coverage. The following processes interact with Entra ID tokens and should NOT be excluded from EDR monitoring:

- `microsoft-identity-broker` (D-Bus service, systemd user unit)
- `linux_entra_bridge.py` (native messaging host, Python process spawned by browser)
- Browser processes (Firefox, Chromium) — handle the PRT SSO cookie

### Application Allowlisting

If the endpoint uses application allowlisting (fapolicyd, AppArmor, or similar):

**RPM install:** The native host at `/usr/libexec/linux-entra-bridge/linux_entra_bridge.py` is installed via RPM and should be automatically trusted.

**Unpacked Chromium extension:** Developer Mode must be enabled, which may conflict with allowlisting policies. If Chromium is locked down:
- Add the unpacked extension path to the allowlist
- Or deploy via the RPM (which installs to a system path)

**Native messaging host:** The Python script must be executable by the browser's user. Verify with:
```bash
ls -la $(cat ~/.mozilla/native-messaging-hosts/linux_entra_bridge.json | python3 -c "import json,sys; print(json.load(sys.stdin)['path'])")
```

### SIEM Integration

The native messaging host logs to stderr (captured by journald when launched from systemd-managed browsers). Security-relevant events (broker failures, authentication errors, rate-limit triggers) can be forwarded to your SIEM via:

```bash
journalctl --user -f | grep -i "entra\|broker\|identity"
```

For structured log forwarding, configure journald to forward to your syslog/SIEM collector.

### Device Loss / Theft Procedures

If a device with an active PRT cookie is lost or stolen:

1. **Immediate:** Intune remote wipe via Endpoint Manager
2. **Token revocation:** Revoke PRT via Entra ID admin portal (Azure AD → Devices → Revoke sessions)
3. **Conditional Access:** Existing CA policies will block the compromised device once Intune marks it non-compliant
4. **Verification:** Confirm device appears as "Non-compliant" / "Disabled" in Entra ID Devices

The PRT cookie has a maximum TTL of 24 hours (capped by the extension). After revocation + 24h, the cookie is definitively expired even if the device is offline.
